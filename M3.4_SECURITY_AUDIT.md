## 2. Detailed Verification Findings

### 2.1 JWT & Device-Token Separation
- **Isolated Secrets:** `validateDeviceJwtSecretsConfig()` in `nexa-backend/src/utils/deviceAuth.utils.js` enforces dedicated `DEVICE_ACCESS_SECRET` and `DEVICE_REFRESH_SECRET` (>= 32 characters in production, distinct from each other and from `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, and `RAT_SECRET`). Production startup fails closed on missing, weak, or colliding secrets.
- **Explicit Type Claims (`typ`):**
  - Device access tokens are signed with `typ: 'nexa_device_access'` (15-minute TTL, `HS256`).
  - Device refresh tokens are signed with `typ: 'nexa_device_refresh'` (7-day TTL, `HS256`).
- **Cross-Boundary Rejection:**
  - `requireAuth` (`nexa-backend/src/middleware/auth.middleware.js`) explicitly rejects any token whose `typ` starts with `nexa_device_` with HTTP `401`.
  - `verifyDeviceAccessToken` and `verifyDeviceRefreshToken` strictly enforce `payload.typ === 'nexa_device_access'` and `payload.typ === 'nexa_device_refresh'`, respectively.

### 2.2 Refresh Rotation & Replay Detection
- **Atomic Rotation:** `rotateDeviceRefreshToken()` in `nexa-backend/src/services/deviceAuth.service.js` uses a single atomic `Device.findOneAndUpdate` pipeline matching `deviceId`, `deviceGeneration`, `isRevoked: false`, `isQuarantined: false`, and an unrotated, unexpired `deviceRefreshTokens` entry (`tokenHash`, `rotatedAt: null`, `expiresAt > $$NOW`).
- **Token Hashing:** Refresh tokens are hashed via `hashToken()` (SHA-256) before storage in `device.deviceRefreshTokens`; raw refresh tokens are never stored in MongoDB.
- **Replay Detection:** If `findOneAndUpdate` returns `null` and the incoming hash matches an entry with `rotatedAt != null`, the backend immediately wipes the entire `deviceRefreshTokens` array, sets `isOnline: false`, and throws `DEVICE_TOKEN_REUSE_DETECTED` (HTTP `401`).
- **Client Single-Flight Coalescing:** `DeviceAuthClient` in `nexa-desktop/src/main/auth/deviceAuthClient.js` coalesces concurrent `authenticate()`, `refreshSession()`, and 401-triggered `authenticatedFetch()` retries so parallel requests do not trigger false-positive refresh replay detections.

### 2.3 Device Ownership & Generation Validation
- **Centralized Guard:** `assertDeviceActiveAndBound()` verifies that the device exists, is not revoked (`isRevoked`), is not quarantined (`isQuarantined`), has no active pairing/recovery lock (`activePairingLock.state`, `pendingResetAuth`, `stagedDeviceToken`), has a non-expired `hashedDeviceToken`, has a valid `userId`, and matches both `expectedGeneration` and `expectedUserId`.
- **Header & Body Binding:**
  - `requireDeviceAuth` validates `X-Device-Id` and `X-Device-Generation` headers against the verified JWT claims when present.
  - `recordDeviceHeartbeat` and `unpairDeviceBySelf` reject body-supplied `deviceId` or `deviceGeneration` mismatches (`403 CROSS_DEVICE_TOKEN_MISUSE` / `401 DEVICE_GENERATION_MISMATCH`).
- **Constant-Time Token Comparison:** `verifyHashedDeviceToken()` uses `crypto.timingSafeEqual()` on SHA-256 hex digests.

### 2.4 Pairing-Code Security
- **Cryptographic Generation:** `generateSecurePairingCode()` in `nexa-backend/src/services/pairing.service.js` uses `crypto.randomBytes(8)` mapped onto a 32-character unambiguous Base32 alphabet (`ABCDEFGHJKLMNPQRSTUVWXYZ23456789`), eliminating modulo bias (`256 % 32 === 0`).
- **Short TTL & Hashed Storage:** Codes expire after 5 minutes (`PAIRING_TTL_MS = 5 * 60 * 1000`) and are hashed with SHA-256 (`hashPairingCode`) before persistence; plaintext codes are not persisted or queried in MongoDB.
- **Single-Use & Rate Limiting:** Claiming a code uses atomic CAS (`isClaimed: false`) so concurrent claims yield a single winner. `POST /api/v1/pairing/claim` is protected by `pairingClaimRateLimiter` (15 requests per 15 minutes in non-test environments). Prior pending sessions for the same user are superseded on new initiation.

### 2.5 DPAPI Credential Storage
- **OS-Backed Encryption:** `SecureStorageService` (`nexa-desktop/src/main/storage/secureStorage.js`) encrypts/decrypts the credential vault (`secure-vault.json`) exclusively in the Electron Main Process using `electron.safeStorage` (Windows DPAPI).
- **Fail-Closed Policy:** Unencrypted plaintext fallback is strictly forbidden; if `safeStorage.isEncryptionAvailable()` is `false`, `DeviceAuthClient.authenticate()` aborts with `NEXA_ERR_ENCRYPTION_UNAVAILABLE`.
- **Atomic Writes & Corruption Quarantine:** Writes use a temporary file + atomic rename; malformed or undecryptable vaults are quarantined without exposing secrets.

### 2.6 Electron IPC Isolation
- **Hardened `BrowserWindow`:** `SECURITY_CONFIG` in `nexa-desktop/src/main/config.js` enforces `contextIsolation: true`, `nodeIntegration: false`, `nodeIntegrationInWorker: false`, `nodeIntegrationInSubFrames: false`, `sandbox: true`, `webSecurity: true`, and `allowRunningInsecureContent: false`.
- **Navigation Guardrails:** `nexa-desktop/src/main/window.js` blocks external `will-navigate` transitions away from `file:` and delegates `window.open` safely.
- **Frozen Preload Bridge & Whitelists:** `nexa-desktop/src/preload/index.js` exposes `window.nexaDesktop` via `contextBridge.exposeInMainWorld` with `Object.freeze()` at every API namespace (`storage`, `pairing`, `deviceAuth`, `heartbeat`). Raw `ipcRenderer`, `require`, and `process` are never exposed. All invoke/receive channels are restricted to explicit `ALLOWED_INVOKE_CHANNELS` (21 channels) and `ALLOWED_RECEIVE_CHANNELS` (7 channels). No `saveCredentials` or `clearCredentials` IPC channels exist.

### 2.7 Device Revocation & Unpair
- **Owner-Authenticated Unpair & Revoke:** `POST /api/v1/device/:deviceId/revoke` and `DELETE /api/v1/device/:deviceId/unpair` require `requireAuth` (user JWT) and enforce `device.userId.toString() === String(userId)` (`403 FORBIDDEN` on cross-user attempts).
- **Atomic Invalidation:** Unpair atomically sets `isRevoked: true`, `isOnline: false`, `hashedDeviceToken: null`, `stagedDeviceToken: null`, `deviceRefreshTokens: []`, `unpairedAt`, `unpairedBy`, and increments `deviceGeneration` by `1` (rendering all existing access, refresh, and device tokens permanently unusable). Repeated unpair calls are idempotent.
- **Desktop Self-Unpair:** `DeviceAuthClient.unpairDevice()` stops `HeartbeatClient`, calls `DELETE /api/v1/device/unpair`, wipes in-memory tokens and the DPAPI vault on success, and coalesces concurrent unpair calls. On backend outage, it preserves DPAPI credentials and reports `remoteRevocationPending: true` so revocation can be retried.

### 2.8 Renderer Credential Isolation
- `nexa:storage-get-device-info`, `nexa:device-auth-get-status`, and `nexa:heartbeat-get-status` return only sanitized metadata (`isPaired`, `deviceId`, `deviceName`, `userId`, `backendUrl`, `pairedAt`, `state`, `expiresAt`, `lastError`).
- `deviceToken`, `accessToken`, and `refreshToken` never cross the IPC boundary and are absent from `DesktopControlPage.jsx` state and DOM.
- `HeartbeatClient` redacts `Bearer ...` and JWT patterns (`eyJ...`) in `sanitizeErrorMessage()` before emitting status events.

## 3. Known Rate-Limiting Limitation (MemoryStore)

`nexa-backend/src/middleware/rateLimit.middleware.js` configures five `express-rate-limit` limiters (`authRateLimiter`, `sessionRateLimiter`, `pairingRateLimiter`, `pairingClaimRateLimiter`, `deviceAuthRateLimiter`) without a `store` option, defaulting to `express-rate-limit`'s in-memory `MemoryStore`.

- **Impact:** In a single-process deployment, rate limits are enforced accurately. In a multi-instance / clustered deployment (e.g., PM2 cluster, Kubernetes replicas, or multiple containers behind a load balancer), each instance tracks counters independently, allowing an attacker to multiply their effective request budget by the number of backend replicas, and counters reset on process restart.
- **Production Requirement:** Configure a shared external store (such as Redis via `rate-limit-redis`) for all `express-rate-limit` instances before scaling `nexa-backend` horizontally.

# NEXA 2.0 — M3.4 Known Limitations & Production Requirements

**Audit Date:** 2026-11-28  
**Scope:** M3.4.1–M3.4.9 Release

---

## 1. Known Limitations

### 1.1 In-Memory Rate Limiting (`MemoryStore`)
- **Location:** `nexa-backend/src/middleware/rateLimit.middleware.js`
- **Detail:** All rate limiters (`authRateLimiter`, `sessionRateLimiter`, `pairingRateLimiter`, `pairingClaimRateLimiter`, `deviceAuthRateLimiter`) use `express-rate-limit` with its default in-memory `MemoryStore`.
- **Limitation:** Rate-limit counters are scoped to a single Node.js process and are lost on server restart. In a horizontally scaled or clustered deployment (multiple backend instances behind a load balancer), each instance maintains separate counters, weakening brute-force protection on `/api/v1/pairing/claim` and `/api/v1/device/auth/*`.
- **Mitigation / Production Requirement:** Configure a shared external store (e.g., Redis via `rate-limit-redis`) before running multiple backend instances.

### 1.2 Windows-Only DPAPI Persistence Scope
- **Location:** `nexa-desktop/src/main/storage/secureStorage.js`
- **Detail:** Desktop credential encryption relies on Electron's `safeStorage` backed by Windows DPAPI (`CryptProtectData`), which binds encrypted vaults to the current Windows user account on the local machine.
- **Limitation:** Encrypted `secure-vault.json` files are non-portable across different Windows user profiles or machines, and non-Windows platforms require an OS keyring/libsecret provider. If `safeStorage.isEncryptionAvailable()` returns `false`, authentication fails closed (`NEXA_ERR_ENCRYPTION_UNAVAILABLE`) with no plaintext fallback.

### 1.3 Web Frontend Polling Interval
- **Location:** `nexa-frontend/src/pages/DesktopControlPage.jsx`
- **Detail:** `DesktopControlPage` refreshes device status from the backend via a 10-second polling interval (`setInterval` at `10000` ms) plus manual refresh, rather than a server-push WebSocket/SSE stream.
- **Limitation:** Remote device state transitions (e.g., `ONLINE` -> `OFFLINE` or remote unpair) may take up to 10 seconds to reflect in the web dashboard unless the user triggers a manual refresh.

### 1.4 Unreachable Backend During Desktop Unpair
- **Location:** `nexa-desktop/src/main/auth/deviceAuthClient.js`, `nexa-desktop/src/main/ipc.js`
- **Detail:** When the user initiates unpair from the Desktop Agent while the backend is unreachable, `unpairDevice()` preserves DPAPI credentials and returns `remoteRevocationPending: true` (`retryable: true`) rather than silently wiping local credentials without server revocation.
- **Limitation:** Full local + remote unpair requires backend connectivity (or an owner-initiated unpair from the web UI).

## 2. Production Deployment Requirements

1. **Provision Isolated Signing Secrets:** Set strong (>= 32 characters), distinct values for:
   - `DEVICE_ACCESS_SECRET`
   - `DEVICE_REFRESH_SECRET`
   - `JWT_ACCESS_SECRET`
   - `JWT_REFRESH_SECRET`
   - `RAT_SECRET`
   *(The backend enforces fail-closed validation when `NODE_ENV=production`.)*
2. **Configure Shared Rate-Limit Store:** Attach a Redis store to `express-rate-limit` in `rateLimit.middleware.js` for multi-instance deployments.
3. **Set CORS & TLS:** Configure `CLIENT_ORIGIN` to the production frontend URL and serve all backend/device API traffic over HTTPS.
4. **MongoDB Connectivity:** Use a MongoDB replica set in production to support multi-document ACID transactions for recovery/pairing state transitions.
